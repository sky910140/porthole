# 产品化可行性基线

日期：2026-09-21  
范围：Task 0 风险验证，只使用测试夹具与临时目录，不修改用户项目。

## 结论

只读能力可以继续产品化；本地自动应用修改可行，但必须经过实时编辑器就绪检查、写前日志和启动恢复。当前发行物仍是需要 Python 的 wheel，独立 Windows 运行包是公开 Beta 的发布阻断项。

当前本机已配置的日常服务在检查时为停止状态，AI Zhagan 的远程 `list_projects` 调用返回内部错误。这证明“曾经调用成功”不能作为当前连接状态，产品必须分别显示本地服务、远程通道、授权和最近真实调用。

## 接入前提矩阵

| 用户状态 | 当前可以完成 | 当前外部准备 | R2 产品行为 |
|---|---|---|---|
| 未配置用户 | 安装源码、运行本机服务、使用测试客户端 | Python 3.11+；若连接网页，还需要可达 MCP 与账号权限 | 安装前说明网页接入前提；提供明确标记的本地示例，不伪装网页已连接 |
| 已有 HTTPS 与 GitHub OAuth | 配置公共地址、所有者账号并连接支持 MCP 的客户端 | 域名／通道、OAuth App、本人稳定账号 ID | 向导验证每一层，并通过真实工具调用完成最终验证 |
| 已完成连接的返回用户 | 重新打开项目并调用工具 | 本地服务和通道需要继续可用 | 复用项目配置；若状态失效只展示一个主要修复动作 |

外部账号开通和域名准备不属于 10 分钟上手指标。产品必须分别记录外部准备时间、界面操作时间和等待时间。

## 实验记录

### 1. 构建与运行方式

- `pip wheel . --no-deps` 成功生成 `project_mcp_assistant-0.1.0-py3-none-any.whl`。
- 当前环境没有 PyInstaller，`python -m PyInstaller --version` 明确失败。
- 因此现有 wheel 不能证明无 Python／Node 的干净机器可运行。Task 3 必须构建并在隔离环境验证 Windows 运行包，失败时不得发布“一键安装”声明。

### 2. 编辑器与磁盘竞争

运行 `node experiments/product-feasibility/editor-probe-run.js`，使用真实 VS Code Extension Host 和复制的夹具文件：

1. 编辑器形成未保存内容；
2. 外部进程修改同一磁盘文件；
3. 编辑器仍保留 dirty 缓冲区，磁盘已经是另一份内容；
4. 进程退出码为 0，断言全部成立。

结论：仅校验磁盘哈希不足以保护未保存缓冲区。本地应用必须要求相关编辑器会话在线且报告当前文档状态；dirty、失联和租约过期属于可重试阻塞，不能静默覆盖。

VS Code 宿主同时输出互斥量和内部通道警告，但测试进程正常退出。正式集成测试应隔离用户数据与扩展目录，并把宿主警告与断言失败分开记录。

### 3. 写入中断与恢复判定

运行 `python experiments/product-feasibility/write-recovery-probe.py`，只操作临时目录。结果：

| 中断点 | 磁盘证据 |
|---|---|
| 日志写入、替换前 | 原始内容 |
| 文件替换后、终态日志前 | 目标内容 |
| 终态日志完成 | 目标内容 |

结论：数据库或日志状态不能单独代表文件状态。恢复必须同时读取事务类型、逐文件阶段和原始／目标字节哈希；替换后的响应丢失不能导致重复应用。

## 继续与降级条件

继续实现统一修改单、执行器和 VS Code 审阅流程。以下任一条件不满足时，v0.3 降级为只读加补丁导出：

- 真实 VS Code 测试不能稳定阻止 dirty、失联和预览后变化的文件；
- 任一故障注入点无法通过日志和哈希确定可恢复状态；
- 独立运行包无法在没有开发运行时的干净 Windows 环境启动；
- 远程提交接口可以绕过本地审阅直接写入文件。

尚未完成的外部验收：新用户观察、真实 ChatGPT 账号重新授权、公共通道断线恢复。它们在 Task 5、10、12 执行，不由本地自动化结果替代。
